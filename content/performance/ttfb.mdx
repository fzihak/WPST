## Symptoms

- Pages take 2–10 seconds to start rendering; the browser shows white for seconds before HTML arrives.
- Admin is sluggish, especially list tables with filters or search.
- TTFB varies wildly: fast on repeat requests, slow on first load.
- PageSpeed/Lighthouse complains about server response time; Core Web Vitals fail on LCP.

## Possible Causes

1. Uncached pages: cache miss ratio high, or logged-in-users bypassing page cache entirely.
2. Slow database queries: missing indexes, autoload bloat, expensive meta queries, unbounded `LIKE`.
3. Blocking external HTTP calls in the render path (shipping rates, currency APIs, CRM lookups, Google Fonts).
4. PHP/FPM saturation: not enough workers, or PHP version/OPcache misconfigured.
5. Heavy hooks: a plugin running expensive work on every request (e.g. rebuilding sitemaps, syncing inventory).
6. Cold object cache after a purge, or memory too small causing constant eviction.
7. Hosting I/O or CPU throttling (shared hosting limits).

## Prerequisites

- A baseline measurement (TTFB, query count, peak memory) taken before changes.
- Query Monitor on staging, plus access to slow query logs.
- Staging to test server settings without audience impact.

## Investigation

1. **Measure each layer separately** with curl: DNS, connect, TLS, time to first byte.

```bash
curl -sS -o /dev/null -w 'dns=%{time_namelookup}s conn=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s total=%{time_total}s size=%{size_download}\n' https://example.com/?nocache=$RANDOM
```

2. **Compare cached vs uncached** to see how much a page-cache hit hides.

```bash
curl -sS -o /dev/null -w 'hit=%{time_starttransfer}s\n' https://example.com/
curl -sS -H 'Cache-Control: no-cache' -o /dev/null -w 'miss=%{time_starttransfer}s\n' "https://example.com/?nocache=$(date +%s)"
curl -sS -H 'Cookie: wordpress_logged_in=1' -o /dev/null -w 'loggedin=%{time_starttransfer}s\n' https://example.com/
```

3. **Use Query Monitor on the slow page** and record: total time, query time, HTTP API time, hook with the highest cumulative time, and peak memory.

4. **Read the slow query log** rather than guessing which query is heavy.

```sql
SET GLOBAL slow_query_log='ON';
SET GLOBAL long_query_time=0.5;
-- then: SHOW PROCESSLIST during the slow request
```

```bash
tail -n 50 /var/log/mysql/slow.log
```

5. **Check for blocking HTTP calls** in the render path (the "adds 2 seconds on every page" class).

```bash
# Site Health → Info, or Query Monitor's HTTP API panel
grep -rn 'wp_remote_get\|wp_remote_post' wp-content/plugins/active-plugin/*.php | head
```

6. **Confirm infrastructure headroom**: FPM queue, CPU steal, disk latency.

```bash
uptime
php-fpm status 2>/dev/null | head
iostat -x 1 3   # or top, if iostat is unavailable
```

## Diagnosis

| Measurement | Conclusion | Fix area |
| --- | --- | --- |
| High `time_namelookup` | DNS slow | resolver/geo-DNS |
| High `time_appconnect` | TLS/SSL handshake | session reuse, OCSP, edge termination |
| TTFB high only on cache miss | PHP/DB render cost | cache strategy + query work |
| Query Monitor shows >1s query time | database | indexes, autoload, meta queries |
| HTTP API time high | external calls | cache/async them |
| Consistent ~1–3s floor everywhere | PHP version/OPcache or I/O | infrastructure |
| Spikes with traffic | saturation | capacity + caching |

::: investigate
Investigation mindset: optimise the largest contributor, not the easiest. Two measurements — cached vs uncached, and Query Monitor's breakdown — usually reveal 80% of the answer in five minutes.
:::

## Resolution

1. **Lift the floor first**: PHP 8.x with OPcache sized correctly, object cache enabled and warm, and page cache covering anonymous traffic.
2. **Attack the database**: add indexes for the slow queries, fix meta-heavy queries, reduce autoloaded options, and remove plugins performing unbounded queries on each load.
3. **Move external calls out of the request**: cache responses in transients or background-refresh via cron/queue, and set short timeouts so a slow third party cannot stall rendering.
4. **Review hooks**: use Query Monitor to find the plugin consuming render time, then update it, replace it, or move its work to a scheduled job.
5. **Fix cache coverage**: exclude only what must be excluded (cart/checkout/account), and support logged-in caching where possible with fragment caching.
6. **Sizing**: give FPM enough workers and memory ([/php/memory-limit](/php/memory-limit)), then verify with a load test rather than an isolated request.

## Verification

- Before/after TTFB numbers documented for: homepage (cold), a product/post page, search, and wp-admin list table.
- Query Monitor: query time and HTTP API time reduced; peak memory unchanged or lower.
- Cache hit ratio ≥ 90% for anonymous traffic on the affected pages.
- Load test (even modest: 20–50 concurrent users) shows no new 5xx and no timeout growth.

## Root Cause

TTFB is a sum: DNS + TLS + server queue + PHP render + database + external calls, plus any cache miss penalties. Without separating these, teams optimise CSS and images while the actual bottleneck is a 3-second uncached query.

## Prevention

- Track TTFB as a monitored metric with p75/p95, not a one-off measurement.
- Add a performance budget to the release process: new plugin, new query, new external call all need measured cost.
- Re-audit autoloaded options and cron jobs quarterly ([/checklists/performance](/checklists/performance)).
- Keep staging data volume realistic — performance bugs hide on empty staging databases.
