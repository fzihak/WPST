## Symptoms

- "Error establishing a database connection" alternating with pages that load partially.
- MySQL log: `Table 'wp_options' is marked as crashed and should be repaired`, `Incorrect key file`, `#145`, `#1194`.
- Random content loss, menus appearing empty, or options silently not saving.
- Queries hanging, followed by connection timeouts.
- Host notice after a disk-full incident or an ungraceful MySQL restart.

## Possible Causes

1. Ungraceful shutdown: power loss, OOM kill, host restart mid-write.
2. Disk full or inode exhaustion while MySQL was writing.
3. MyISAM tables (legacy) with no crash safety — one of the main reasons to migrate to InnoDB.
4. Hardware/storage faults or a corrupted InnoDB tablespace.
5. A runaway query or a plugin writing invalid data (rarely corruption, often "broken content").
6. Restoring files without the matching database dump (mismatched state).

## Prerequisites

- **A snapshot you control**: file-level copy or a full dump before any repair.
- `mysql` CLI access (phpMyAdmin works but CLI gives real errors).
- Free disk space for repair operations and temporary files.
- Confirmation of the storage engine of the affected tables.

## Investigation

1. **Freeze the state**: stop writes so the snapshot is meaningful.

```bash
wp maintenance-mode activate
mysqldump --single-transaction --routines --triggers dbname > /home/user/backups/pre-repair.sql
ls -lh /home/user/backups/pre-repair.sql
```

2. **Identify the engine and check every WordPress table** before repairing anything.

```sql
SELECT TABLE_NAME, ENGINE, TABLE_ROWS, DATA_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME LIKE 'wp_%';
CHECK TABLE wp_options, wp_posts, wp_postmeta, wp_usermeta, wp_terms;
```

3. **Read MySQL's own error log** for the mechanism rather than guessing.

```bash
tail -n 120 /var/log/mysql/error.log
grep -iE 'corrupt|crash|innodb|disk full' /var/log/mysql/error.log | tail -20
df -h && df -i
```

4. **Check for the WordPress-side symptoms** that usually accompany corruption.

```bash
wp db check
wp option get siteurl
wp post list --post_type=post --format=count
wp db query "SELECT COUNT(*) FROM wp_options WHERE autoload='yes';"
```

## Diagnosis

| Scenario | Storage Engine | Log Signature / Symptom | Strategy |
| --- | --- | --- | --- |
| MyISAM crashed table | MyISAM | `Table is marked as crashed` / error #145 | `REPAIR TABLE`, then migrate to InnoDB |
| InnoDB single-table corrupt | InnoDB | Page checksum mismatch in error log | Logical rebuild: export data, recreate table, reimport |
| InnoDB tablespace/redo corruption | InnoDB | Server crash loop on boot, assertion failure | Force recovery mode (`innodb_force_recovery=1..4`) to dump, then restore |
| Physical storage / I/O fault | Any | OS kernel I/O errors (`dmesg`), sector failure | Snapshot immediately, evacuate to new host/storage |
| Logical inconsistency (content wrong) | Any | Orphaned rows in `wp_postmeta`, missing terms | SQL cleanup or snapshot rollback (not engine corruption) |

::: danger
Never run `REPAIR TABLE` on InnoDB as a "fix" and never delete files in the MySQL data directory to clear an error. Both turn a recoverable problem into data loss. Snapshot first, always.
:::

::: investigate
Investigation mindset: corruption has a *cause* — disk, crash, storage, engine. Repairing the symptom while the cause persists guarantees a repeat, and often the second incident takes data with it.
:::

## Resolution

1. **Repair cleanly, engine-appropriately:**

```sql
-- MyISAM only
REPAIR TABLE wp_options;
OPTIMIZE TABLE wp_postmeta;

-- InnoDB: prefer a logical rebuild instead of REPAIR
-- 1) dump the table, 2) drop/recreate via import, keeping the dump
mysqldump dbname wp_options > wp_options.sql
-- (verify the dump opens and contains INSERT statements before dropping)
```

2. **Restore-based recovery**: if the affected table is `wp_options` or `wp_posts` and you have a recent dump, importing that single table is usually faster and safer than repairing.
3. **Migrate legacy engines to InnoDB** to reduce future risk:

```sql
ALTER TABLE wp_options ENGINE=InnoDB;
```

4. **Free space** if disk/inode exhaustion triggered the crash, and verify MySQL starts cleanly afterwards.
5. **If InnoDB recovery mode is needed** (`innodb_force_recovery` 1–6), do it only on a copy, take a dump immediately, and never leave the setting enabled on production.
6. **After repair, verify data integrity**: counts, options, users, recent posts and orders — compare with expectations before reopening the site.
7. **Remove maintenance mode** and re-enable monitoring.

## Verification

- `CHECK TABLE` on all WordPress tables returns OK; `wp db check` is clean.
- No new corruption errors for 24 hours including a MySQL restart.
- Site functions: login, publish a post, place a test order (if WooCommerce), run cron.
- Backups themselves are verified: restore the post-repair dump into a scratch database and browse it.

## Root Cause

MySQL crashes mid-write or runs out of space, leaving incomplete pages/redo state; MyISAM tables have no crash-safe recovery, so they surface as "crashed" tables. Storage-level faults produce the same symptoms without an obvious trigger.

## Prevention

- Always InnoDB; check for leftovers with `SHOW TABLE STATUS` in the quarterly DB audit.
- Monitor disk/inode usage with an 85% alert threshold.
- Use `mysqldump`, not file copies, for logical backups; verify restores.
- Investigate every "MySQL restarted unexpectedly" event instead of dismissing it.
- Keep MySQL/MariaDB patched, check the error log weekly, and run an optimize/cleanup pass on a schedule.
