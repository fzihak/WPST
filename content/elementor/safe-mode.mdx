## Symptoms

- The Elementor editor loads forever, or widgets do not respond to drag/drop.
- Editor works but the published page renders differently (layout drift, missing styles).
- A specific widget breaks only on some pages.
- Frontend loads for admins but fails for visitors (cache interaction).

## Possible Causes

1. A plugin conflict inside the editor (third-party widget add-ons, optimisation plugins, security plugins).
2. Theme conflict: the theme's templates or CSS clash with Elementor's markup.
3. Editor asset failures (JS/CSS 404, blocked REST requests).
4. Server limits during editor requests: memory, `max_input_vars`, timeouts.
5. Cache/optimiser serving stale editor assets or refactoring its JS.
6. A corrupted template/kit referenced by the page.

## Prerequisites

- Elementor → Tools access (Safe Mode toggle), or the ability to add a URL switch.
- Awareness that Safe Mode affects **your session only** while active in the editor; some setups also apply it site-wide via the experiments area.

## Investigation

1. **Enable Safe Mode** from Elementor → Tools (or the editor's own prompt) and reload the failing page.
2. **Interpret the outcome:**

| Safe Mode result | Meaning | Next step |
| --- | --- | --- |
| Everything works | A plugin or the theme is the cause | re-enable half at a time in a regular session |
| Still broken | Elementor/kit/server level | check assets, limits, cache, template |
| Works but styling differs | theme CSS | test a default theme with the same content |

3. **Capture editor-side errors** — the browser console and REST responses are the evidence.

```bash
# editor requests go through REST; verify they answer
curl -sSI https://example.com/wp-json/elementor/v1/globals | head -3
tail -f wp-content/debug.log
```

4. **Check the server side** because editor requests are heavy.

```bash
wp eval 'echo ini_get("memory_limit")." / ".ini_get("max_input_vars")."\n";'
grep -iE 'fatal|memory|timeout' ~/logs/php_error.log | tail -20
```

5. **Then reproduce in a normal session** with halving to name the exact conflicting plugin ([plugin conflict](/plugins/plugin-conflict)).

## Diagnosis

- Editor fails, Safe Mode fixes it, one plugin re-enables the failure → editor plugin conflict.
- Editor fine, published page wrong → CSS generation/delivery ([Elementor CSS article](/elementor/css-not-loading)).
- Editor spinner with 500 on REST → memory/limit or a fatal in a widget.
- Editor works in Safe Mode and also with all plugins, but only on staging → cache/optimiser or OPcache stale code.

::: investigate
Investigation mindset: Safe Mode is a *test*, not a fix (though it is also one, permanently available as a site-wide safe mode for a broken frontend). Use it to answer one question: does Elementor alone render correctly?
:::

## Resolution

1. Name the conflicting plugin via halving, then update it; add-on widgets are the usual suspect.
2. If the theme is the cause, test with a default theme and move custom markup into Elementor templates rather than theme PHP.
3. If the editor is resource-starved: raise memory to 512M for builder sites, `max_input_vars` to 5000+, and `max_execution_time` to 300.
4. Fix asset caching: exclude Elementor files from minify/combine and purge caches after any Elementor/kit change.
5. If a specific template is corrupted, re-save it, or rebuild the section inside a new page and replace the template reference.
6. Leave Safe Mode only when a real fix is in place; document which plugin was responsible in the ticket.

## Verification

- Editor loads and saves with plugins active; frontend matches the editor preview.
- No fatal/limit errors during a full edit-save-reload cycle.
- Publish a test page and view it in a private window to confirm delivery without admin session.
- Re-check after a cache purge so the fix is not cache-dependent.

## Root Cause

Elementor's editor is a JS application making heavy REST API calls within a full WordPress request; any plugin, theme or server limit on that path becomes an editor failure.

## Prevention

- Keep Elementor + add-ons updated together, on staging first.
- Budget memory/limits for builder sites and verify in the environment sizer ([tools](/tools)).
- Limit the number of widget add-ons; fewer extensions, fewer conflicts.
- Keep a documented "Safe Mode checklist" so any engineer can triage in minutes.
