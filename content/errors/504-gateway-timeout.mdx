## Symptoms

- Browser renders `504 Gateway Timeout`, `504 Gateway Time-out`, or Cloudflare "Error 504: Gateway Timeout".
- The request hangs for exactly 30, 60, or 120 seconds before failing with an empty or HTML error response.
- The failure targets heavy operations: WooCommerce checkout submission, CSV/product imports, WP-Admin bulk updates, plugin activations, or analytics reports.
- Static assets (CSS, JS, images) load immediately with HTTP `200`, but dynamic PHP requests hang and abort.
- `curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' https://example.com/` returns `504` after exactly reaching the proxy timeout threshold.

## Possible Causes

1. **PHP-FPM worker execution timeout**: The script runtime exceeds `max_execution_time` or `request_terminate_timeout` while executing heavy queries or loops.
2. **Reverse proxy read timeout**: NGINX `fastcgi_read_timeout` or `proxy_read_timeout` is shorter than the time required for PHP-FPM or Apache to respond.
3. **External HTTP API hang**: A plugin initiates a synchronous outbound request (`wp_remote_get` or `cURL`) to an external service without a strict connection timeout.
4. **Database lock contention**: An open MySQL transaction or unindexed query blocks table rows (`wp_posts`, `wp_options`, `wp_wc_orders`), locking worker threads until timeout.
5. **Edge CDN proxy limit**: Cloudflare or Fastly imposes a strict 100-second edge-to-origin HTTP timeout on HTTP connections.
6. **Worker thread exhaustion**: All available PHP-FPM child processes (`pm.max_children`) are occupied by slow requests, queuing new requests until the connection queue times out.

## Prerequisites

- SSH or terminal access with `sudo` privileges to inspect web server and PHP-FPM configurations.
- Access to NGINX/Apache error logs and PHP-FPM slow logs (`/var/log/nginx/error.log`, `/var/log/php-fpm.log`).
- Ability to run diagnostic WP-CLI commands and query MySQL process list directly.
- Staging environment or active full site backup before altering server process pools or timeout thresholds.

## Investigation

1. **Measure the exact failure latency**: Run `curl` with timing output to determine if the timeout matches a default configuration value (e.g., 30s, 60s, 100s, or 300s).

```bash
time curl -sS -o /dev/null -w 'HTTP %{http_code} | Total: %{time_total}s | DNS: %{time_namelookup}s | Connect: %{time_connect}s\n' https://example.com/heavy-page/
```

2. **Inspect reverse proxy error logs**: Identify the upstream layer that closed the socket.

```bash
# NGINX upstream timeout signatures
grep -Ei 'upstream timed out|connection timed out|504' /var/log/nginx/error.log | tail -n 25

# Apache reverse proxy timeout signatures
grep -Ei 'proxy: error reading status line|AH00898|AH01075' /var/log/apache2/error.log | tail -n 25
```

3. **Check PHP-FPM worker status and slow query logging**: Enable and inspect the PHP slowlog to catch the exact file, line number, and stack trace of stalled scripts.

```bash
# Check if PHP-FPM slowlog is enabled
grep -E 'slowlog|request_slowlog_timeout' /etc/php/*/fpm/pool.d/*.conf

# View live slowlog traces
tail -n 60 /var/log/php*-fpm.slow.log
```

4. **Inspect active database transactions and thread states**: Verify if PHP is waiting on a stalled MySQL table lock or an unindexed query.

```sql
-- Run inside mysql CLI
SHOW FULL PROCESSLIST;
SELECT trx_id, trx_state, trx_started, trx_query 
FROM information_schema.innodb_trx 
ORDER BY trx_started ASC;
```

5. **Test origin server directly (bypassing Cloudflare/CDN)**: Prove whether the 504 is generated by the edge CDN or origin web server.

```bash
# Replace ORIGIN_IP with the server's public IP
curl -sS -k -o /dev/null -w '%{http_code} in %{time_total}s\n' --resolve example.com:443:ORIGIN_IP https://example.com/failing-endpoint/
```

::: investigate
Investigation mindset: A 504 is fundamentally an **asynchronous boundary mismatch**. One layer (the proxy) gave up waiting for the next layer (PHP-FPM, DB, or external API). Never blindly bump timeouts to 600s—trace which specific resource or remote call blocked the worker.
:::

## Diagnosis

| Log / Diagnostic Signature | Failure Boundary | Root Cause |
| --- | --- | --- |
| NGINX: `upstream timed out (110: Connection timed out) while reading response header from upstream` | NGINX ↔ PHP-FPM | PHP script took longer than `fastcgi_read_timeout` (usually 60s) |
| Cloudflare: `Error 504 Gateway Timeout` after exactly 100s | Cloudflare ↔ Origin | Origin server took >100 seconds; Cloudflare hard edge limit triggered |
| PHP Slowlog: `wp_remote_get()` / `curl_exec()` at line X | PHP ↔ External API | Synchronous third-party API (shipping gateway, licensing, webhook) hung |
| MySQL: Query state `Waiting for table metadata lock` or `Updating` | PHP ↔ MySQL | Long transaction or unindexed update query holding row/table locks |
| NGINX: `upstream timed out while connecting to upstream` | NGINX ↔ Socket | PHP-FPM queue full; all workers busy, backlog buffer timed out |

## Resolution

1. **Tune NGINX FastCGI timeouts (Temporary relief for critical operations)**:
   If an administrative import or data migration legitimately needs extended processing time, adjust the NGINX location block:

```nginx
# /etc/nginx/sites-available/example.com
location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/run/php/php8.2-fpm.sock;
    
    # Extend timeouts for long-running WordPress processes
    fastcgi_connect_timeout 60s;
    fastcgi_send_timeout 180s;
    fastcgi_read_timeout 180s;
    
    # Buffer tuning to prevent worker stalling
    fastcgi_buffer_size 128k;
    fastcgi_buffers 4 256k;
    fastcgi_busy_buffers_size 256k;
}
```

Then validate and reload NGINX:
```bash
nginx -t && systemctl reload nginx
```

2. **Synchronize PHP-FPM and PHP runtime limits**:
   Ensure `php.ini` and PHP-FPM pool directives do not kill scripts prematurely:

```ini
; /etc/php/8.2/fpm/php.ini
max_execution_time = 180
max_input_time = 180
memory_limit = 512M
```

```ini
; /etc/php/8.2/fpm/pool.d/www.conf
request_terminate_timeout = 180s
request_slowlog_timeout = 5s
slowlog = /var/log/php-fpm.slow.log
```

Apply changes:
```bash
systemctl restart php8.2-fpm
```

3. **Enforce outbound HTTP request timeouts in WordPress**:
   Prevent hanging remote calls by enforcing a strict global timeout filter via an `mu-plugin`:

```php
<?php
/**
 * Plugin Name: Enforce Safe Outbound HTTP Timeouts
 * Description: Prevents 504 timeouts caused by hanging third-party external APIs.
 */
add_filter( 'http_request_args', function( $args, $url ) {
    // If no timeout or excessive timeout set by plugin, cap at 15 seconds
    if ( empty( $args['timeout'] ) || $args['timeout'] > 15 ) {
        $args['timeout'] = 15;
    }
    return $args;
}, 10, 2 );
```

4. **Kill blocked database transactions**:
   If `SHOW FULL PROCESSLIST` exposes queries executing for >300 seconds:

```sql
-- Terminate rogue locking query by ID
KILL 14892;
```

5. **Offload long operations to Action Scheduler or WP-CLI**:
   Bulk updates, image regenerations, and order syncs should never execute synchronously in an HTTP web request. Execute them via WP-CLI:

```bash
wp wc product update $(wp wc product list --format=ids) --user=1
wp media regenerate --yes
```

## Verification

- Re-run the failing request and verify HTTP `200` status with total time recorded:
  ```bash
  curl -sS -o /dev/null -w 'Status: %{http_code} | Duration: %{time_total}s\n' https://example.com/heavy-page/
  ```
- Check NGINX error logs to confirm zero `upstream timed out` entries during concurrent page requests.
- Monitor PHP-FPM slowlog (`/var/log/php-fpm.slow.log`) to verify no functions exceed 5 seconds.
- Confirm MySQL `SHOW FULL PROCESSLIST` maintains zero locked or unindexed long-running queries.

## Root Cause

A 504 Gateway Timeout occurs when an intermediary proxy or gateway drops a connection because the downstream processing layer breached its maximum waiting threshold. The architectural root cause is almost always synchronous execution of heavy batch workloads, database lock contention, or unbounded external network calls executed directly inside the user-facing HTTP request lifecycle.

## Prevention

- Decouple long-running jobs from HTTP requests using WP-Cron, Action Scheduler, or dedicated background queue workers (Redis/RabbitMQ).
- Set proactive alerts on PHP-FPM active processes and slowlog executions.
- Enforce strict 5-15s timeouts on all outbound `wp_remote_get()` and `wp_remote_post()` API calls.
- Optimize MySQL database indexes on high-churn tables (`wp_options`, `wp_postmeta`, `wp_actionscheduler_actions`).
- If using Cloudflare or an edge CDN, ensure your origin server finishes dynamic requests well inside the edge limit (<100 seconds).
